# Commodore 64

`c64KoalaPlugin` reads and writes the standard 10003-byte Koala multicolor
layout. Native logical resolution is 160×200 with a 2:1 pixel aspect.
`c64ArtStudioPlugin` handles the 320×200 hires Art Studio layout.
`c64DoodlePlugin` handles the 9218-byte Doodle memory image with screen data at
the `$5C00` load base and bitmap at `$6000`.

`c64RawPlugin` supports `hires-bitmap`, `multicolor-bitmap`, `standard-char`,
`multicolor-char`, and `extended-background-char`. Headerless bitmap modes need
`components.screen`; multicolor also needs `components.colorRam` and may include
one-byte `components.background`. Character modes need `components.charset` and
may include screen, color RAM, and background registers.
Automatic arbitrary-RGBA conversion is available for bitmap modes. Charset
modes require native charset/screen components because automatic conversion
would have to invent and deduplicate glyph assets.

`c64Palette` is the canonical PAL-oriented preview palette. Native color codes
are preserved, so applications may pass a different palette/profile.
`c64Plugins` contains all four C64 codecs. Sprite and executable PRG formats are
not supported.

## Native color-code matching

For controlled conversion, pass `ConversionOptions.c64` with a 16-entry
`displayPalette`. Each palette index is the corresponding native VIC-II color
code; the display RGB values never alter the codes written to C64 bytes. The
converter matches unassigned source RGB colors in OKLab, uses the lower code for
an exact tie, and reports the mapping as `c64-color-code-map`.

`sourceColorCodes` associates a source RGB value with a specific native code.
Set `pinned: true` when that code must survive C64 cell packing. A pinned Hires
cell may contain at most two codes. A pinned Multicolor cell may contain at most
three non-background codes; the converter selects a shared background that
satisfies every cell, or throws `VALIDATION_FAILED` with the cell coordinates
and conflicting codes.

```ts
const converted = await registry.convert(source, c64KoalaTarget, {
  dither: "none",
  c64: {
    displayPalette: myVicIiPalette,
    sourceColorCodes: [
      { sourceColor: { r: 63, g: 94, b: 120 }, colorCode: 6, pinned: true }
    ]
  }
});
```

The decoded conversion result uses `myVicIiPalette` for its preview while its
indices and emitted bytes still carry native codes. Re-encoding a decoded C64
raster also uses those native indices directly, rather than rematching preview
RGB values. A configured conversion between native C64 rasters keeps those
indices and optional pins when the target dimensions already match. Native C64
resize is rejected explicitly rather than silently rematching preview RGB.
The `c64-color-code-map` report lists each source RGB value, native code,
OKLab distance, and pin state for auditability.

`borderColorCode` optionally records the separate VIC-II border register during
configured C64 conversion. It must be an integer from 0 through 15. A supplied
code is returned as `metadata.c64BorderColorCode` and the one-byte
`components.border`; it is not bitmap data or the Multicolor shared background.
Omitting it preserves existing C64 output bytes and does not create a border
component.

## C64 Raw bitmap memory

Select `c64.raw` with mode `hires-bitmap` or `multicolor-bitmap` when a C64
program expects memory components rather than a Koala, Art Studio, or Doodle
container. Both bitmap modes are fixed at 40×25 cells and 200 pixel rows. Hires
is 320×200 with an 8×8-pixel cell and two colors per cell. Multicolor is
160×200 logical pixels with a 4×8-pixel cell, four colors per cell, and one
background color shared by the whole image.

For an artist workflow, prepare the exact canvas size, analyze the target, and
fix cell-color findings when exact control matters. Auto conversion can choose
native VIC-II codes and optimize each cell, but review small text, outlines,
and the shared Multicolor background before export. C64 Raw does not expose or
accept the Amiga `amigaPlanar.layout` selector: these are fixed VIC-II bitmap
and attribute components, not selectable bitplane layouts.

### Hires component map

The primary file returned by `c64RawPlugin.encode()` is exactly the 8000 bytes
also retained as `components.bitmap`. Keep `components.screen` as a separate
1000-byte file or place it at the address expected by the receiving program.

For cell `(cx, cy)`, where `cx` is 0–39 and `cy` is 0–24:

- `cell = cy * 40 + cx`.
- Its eight bitmap bytes start at `cell * 8`; byte `cell * 8 + row` represents
  row 0–7. Bit 7 is the leftmost pixel and bit 0 the rightmost.
- Screen byte `screen[cell]` stores the foreground VIC-II color in the high
  nibble and background color in the low nibble.
- A bitmap bit of 1 selects the high-nibble foreground; 0 selects the
  low-nibble background.

There is no screen data appended to the 8000-byte Raw primary file. Pass the
separate component back as `components.screen` when decoding.

```ts
const decoded = await registry.decode(bitmapBytes, {
  formatId: "c64.raw",
  modeId: "hires-bitmap",
  components: { screen: screenBytes }
});
```

### Multicolor component map

The Multicolor primary file is again only the 8000-byte `components.bitmap`.
Preserve three separate sidecars: `components.screen` (1000 bytes),
`components.colorRam` (1000 bytes), and `components.background` (one byte; only
the low nibble is a VIC-II color code).
An optional one-byte `components.border` sidecar is sanitized to its low-nibble
VIC-II border code and retained as `metadata.c64BorderColorCode`; it is not
serialized into the Raw primary bitmap file.

Address each cell with the same `cell = cy * 40 + cx` formula. Its eight bitmap
bytes begin at `cell * 8`. Each byte contains four two-bit logical pixels, most
significant pair first: bits 7–6, 5–4, 3–2, then 1–0. Pair values select:

| Pair | Color source |
| --- | --- |
| `00` | one global `background[0] & 0x0f` |
| `01` | `screen[cell]` high nibble |
| `10` | `screen[cell]` low nibble |
| `11` | `colorRam[cell]` low nibble |

The complete logical native data therefore consists of bitmap 8000 + screen
1000 + color RAM 1000 + background 1 = 10001 bytes, but these are separate Raw
components rather than fixed offsets inside one returned file. A Koala
container wraps the same four payloads after its two-byte load address, which
is why its total size is 10003 bytes.

```ts
const decoded = await registry.decode(bitmapBytes, {
  formatId: "c64.raw",
  modeId: "multicolor-bitmap",
  components: {
    screen: screenBytes,
    colorRam: colorRamBytes,
    background: Uint8Array.of(backgroundCode)
  }
});
```

If a Hires screen component is shorter than 1000 bytes, or either Multicolor
1000-byte component is truncated, decode fails. Omitting a required component
produces `MISSING_HINT`. Keep the exact component names and lengths in project
metadata so a headerless bitmap can be reconstructed without guessing.
